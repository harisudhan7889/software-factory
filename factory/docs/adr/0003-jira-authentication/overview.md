# ADR-0003 — Jira Authentication and Authorization for Provisioning

## Status

Accepted

## Date

2026-11-16

## Authors

Hari

## Context

RFC-0005 — Jira Project Provisioning requires the software factory to
authenticate with Jira so that it can inspect whether a project exists and,
with explicit user approval, create a new Jira project.

The `ticket` skill already authenticates to Jira today, for issue-level
operations only (create, update, transition, comment), using:

- `JIRA_BASE_URL`
- `JIRA_EMAIL`
- `JIRA_API_TOKEN`

supplied as global environment variables, with HTTP Basic Auth
(`email:api_token`) against the Jira Cloud REST API (`/rest/api/3/...`).
This convention exists only as skill documentation (`skills/ticket/SKILL.md`,
`skills/ticket/scripts/jira-create.sh`); it has never been formalized as an
ADR, unlike GitHub authentication (ADR-0001).

Jira project creation requires a broader permission than issue creation:
Jira Cloud gates project creation behind a **site-level ("Create projects")
global permission**, which is a materially different authorization scope
than the project-scoped "Create issues" permission the `ticket` skill
already relies on. RFC-0005 identifies this as an architectural decision
and leaves it to this ADR.

## Decision

Formally adopt the existing **email + API token (Basic Auth)** convention
as the factory's Jira authentication mechanism, and extend its documented
scope from issue-level operations to project-level provisioning operations.

No new authentication mechanism is introduced. The same `JIRA_BASE_URL` /
`JIRA_EMAIL` / `JIRA_API_TOKEN` environment variables, sourced the same
way (global shell environment, never project-local `.env`), are used for
both issue operations (`ticket` skill) and project provisioning (`factory`
skill's Jira provisioning capability).

The factory requires that the Jira account identified by `JIRA_EMAIL` hold
the site-level "Create projects" global permission before attempting
project creation. The factory does not request or manage this permission;
it is granted by the user's Jira site administrator outside the factory,
exactly as the GitHub PAT's scopes are configured by the user outside the
factory (ADR-0001).

The factory will not treat possession of valid Jira credentials as
permission to perform every available Jira operation. Each factory
operation must still enforce its own approval and safety rules.

## Authentication and authorization model

The factory authenticates to Jira using HTTP Basic Auth with the
configured email and API token.

Authentication and authorization are treated as separate concerns,
consistent with ADR-0001's GitHub model:

- Authentication establishes that the factory is acting as the configured
  Jira identity.
- Authorization determines whether that identity has the permission
  required for the requested operation (issue-level vs. project-level).

The factory should verify the required permission before attempting
project creation where practical — for example, a best-effort
`mypermissions` check — rather than discovering an authorization failure
only after attempting creation. A permission check that cannot be
determined conclusively must be reported as unverified, not treated as a
pass.

The factory must not assume that successful authentication means every
requested operation, including project creation, is authorized.

## Credential handling

The Jira API token is provided through the user's shell environment,
exactly as described for `JIRA_BASE_URL` / `JIRA_EMAIL` / `JIRA_API_TOKEN`
today.

The token must:

- Never be committed to Git.
- Never be stored in `.factory/project.yml`.
- Never be written to application source code.
- Never be written to logs.
- Never be included in Jira comments.
- Never be included in pull-request descriptions.
- Never be printed as part of factory status or error reports.

The factory should avoid exposing the token through command output or
error messages generated by `curl` or other API tooling. Scripts must mask
or omit credential values in all diagnostic output, consistent with the
masked-diagnostics pattern used for GitHub authentication (ADR-0001,
"Execution environments").

Only `JIRA_PROJECT_KEY` may come from a project-local `.env` file. Shared
credentials must never be read from a project-local file, so that a
project's `.env` cannot override or shadow the globally configured
identity. This matches the existing `jira-create.sh` behavior and is
extended unchanged to the new project-provisioning scripts.

## Permissions

The factory requires two distinct Jira permission levels depending on the
operation:

| Operation | Required permission |
| --- | --- |
| Create/update/transition/comment on an issue (`ticket` skill) | Project-scoped "Create issues" / "Edit issues" / "Transition issues" / "Add comments" |
| Create a Jira project (`factory` Jira provisioning capability) | Site-level "Create projects" global permission |

The factory must use the minimum permission required for the operation it
is performing. Project-level provisioning scripts must not be invoked for
issue-level operations, and vice versa.

The exact endpoint-level requirements must be verified during
implementation against the Jira Cloud REST API being used.

Permissions must not be broadened merely for convenience. When a future
factory capability requires an additional Jira permission (for example,
project deletion or permission-scheme management), the permission change
must be reviewed rather than silently assumed to already be covered by
this ADR.

## Factory approval boundaries

Authentication with Jira does not grant the factory unrestricted authority
to act.

### Safe actions

The factory may automatically perform safe, non-destructive actions such
as:

- Reading whether a Jira project with a given key exists.
- Reading a Jira project's configured issue types.
- Reading the authenticated identity's permissions (best-effort).
- Reading issue state for existing tickets (already covered by the
  `ticket` skill).

### High-risk or externally visible actions

The factory must request explicit approval before:

- Creating a Jira project.
- Adopting an existing Jira project found under the expected name (i.e.
  recording its key locally) instead of creating a new one.
- Overwriting a previously recorded `JIRA_PROJECT_KEY`.

Jira project creation is treated with the same approval rigor RFC-0001 and
ADR-0001 require for GitHub repository creation.

## Project factory metadata

Jira provisioning will record project-level metadata in
`.factory/project.yml`, alongside any existing GitHub metadata, for
example:

    factory:
      version: "1"

    jira:
      baseUrl: <jira-base-url>
      projectKey: <JIRA-KEY>
      projectName: <project-name>

The metadata must not contain:

- The Jira API token.
- The Jira account email beyond what is already visible in
  `JIRA_EMAIL` (not duplicated into this file).
- Any other credential or secret.

The metadata is a cached representation of factory-managed project state,
not the authoritative source of truth for Jira. The factory must verify
external state (per RFC-0005) rather than blindly trusting the metadata.

## Idempotency

Jira provisioning operations should be safe to retry, following the same
model as ADR-0001's GitHub idempotency rules:

- An existing, resolvable Jira project must not result in another project.
- A correctly recorded `JIRA_PROJECT_KEY` must not be overwritten without
  approval.
- A failed operation should be retryable from the last known successful
  stage.

## Alternatives considered

### Jira Cloud OAuth 2.0 (3LO) app

**Advantages:**

- Scoped, revocable access tied to an installed app rather than a personal
  token.
- Better long-term fit if the factory becomes multi-user or needs to act
  on behalf of different Jira identities.

**Disadvantages:**

- Requires registering and maintaining a Jira Cloud app, an OAuth consent
  flow, and token refresh handling.
- Significant added complexity for the current single-user, single-site
  factory.

**Decision:**

Not selected for the first version. May be reconsidered if the factory
expands to multiple Jira sites or multiple users.

### Email + API token (Basic Auth)

**Advantages:**

- Already in production use by the `ticket` skill; no new credential
  model to introduce.
- Simple to configure for a single developer's Jira Cloud account.
- Low implementation complexity; reuses existing scripts and conventions.

**Disadvantages:**

- Tied to one Jira user's identity and whatever permissions their
  administrator has granted.
- Token lifecycle and rotation are the user's responsibility.
- Project creation requires a site-level permission grant that is outside
  the factory's control or visibility until attempted.

**Decision:**

Selected. Formalizes existing practice rather than introducing a new
mechanism, and keeps the factory's Jira integration, provisioning, and
operation capabilities on one consistent authentication model.

### Jira personal access token (PAT) for Jira Data Center/Server

**Advantages:**

- Would align naming with GitHub's PAT model.

**Disadvantages:**

- Not applicable: the factory targets Jira Cloud (`JIRA_BASE_URL` pointing
  at an `*.atlassian.net`-style site), which uses email + API token, not
  the Data Center/Server PAT mechanism.

**Decision:**

Not applicable to the current Jira Cloud target. Would need its own ADR if
the factory ever targets Jira Data Center/Server.

## Consequences

### Positive

- No new credential model or script rewrite required; existing `ticket`
  skill scripts and conventions are reused unchanged.
- A single, documented Jira authentication story covers both issue
  operations and project provisioning.
- Credentials remain outside the project repository and outside
  `.factory/project.yml`.
- Human approval remains the authority for externally visible and
  potentially destructive Jira operations.

### Negative

- The Jira identity's "Create projects" permission is granted and managed
  entirely outside the factory; a missing grant surfaces only as an
  authorization failure at creation time (mitigated by a best-effort
  pre-check per RFC-0005).
- The approach remains single-user, single-Jira-site; it does not by
  itself support multiple Jira sites or multiple factory users.

## Security considerations

- Use email + API token over HTTPS only; never log the token.
- Keep the token in the user's shell environment, never in a project-local
  file.
- Never commit the token.
- Never store the token in `.factory/project.yml`.
- Never expose the token in logs, Jira comments, GitHub issues, pull
  requests, or reports.
- Require approval for project creation and for adopting/overwriting an
  existing recorded project key.
- Fail safely when authentication or authorization fails; do not retry
  destructively.

## Future migration

This ADR is scoped to the factory's first single-user, single-Jira-site
provisioning capability (RFC-0005).

When the factory expands to support multiple Jira sites, multiple
developers, or hosted/shared factory execution, the authentication model
should be re-evaluated, and a future ADR may select OAuth 2.0 (3LO) or
another mechanism better suited to those requirements.

Changing the authentication mechanism should not require changing the
factory's higher-level provisioning model defined in RFC-0005.
