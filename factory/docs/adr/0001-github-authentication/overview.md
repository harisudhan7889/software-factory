# ADR-0001 — GitHub Authentication and Authorization

## Status

Accepted

Amended 2026-08-22 (non-interactive execution environments; see Amendments)

## Date

2026-08-21

## Authors

Hari

## Context

RFC-0001 — GitHub Repository Provisioning requires the software factory to
authenticate with GitHub so that it can inspect repositories and, with
explicit user approval, create and configure repositories.

The first version of the factory will operate against the developer's
personal GitHub account. GitHub organization support is a future extension.

The factory needs to support the following GitHub capabilities:

- Inspect repositories.
- Create repositories.
- Configure repositories.
- Push code.
- Create pull requests.

The factory must use the minimum permissions necessary for these
capabilities and must protect credentials from exposure in source code,
logs, Jira comments, and reports.

RFC-0001 identifies GitHub authentication as an architectural decision and
leaves the authentication mechanism open.

## Decision

Use a **fine-grained GitHub Personal Access Token (PAT)** for the first
version of the software factory's GitHub integration.

The PAT will authenticate the factory against the developer's personal
GitHub account.

The token will be supplied to the factory through the user's shell
environment, sourced from `.zshrc`, rather than being stored in the project
repository or factory source code.

The factory will use only the minimum GitHub permissions required for its
implemented capabilities.

The factory will not treat possession of the PAT as permission to perform
every available GitHub operation. Each factory operation must still enforce
its own approval and safety rules.

GitHub App authentication may be reconsidered when the factory expands to
support GitHub organizations, multiple users, or other requirements that
make a GitHub App more appropriate.

## Authentication and authorization model

The factory authenticates to GitHub using a fine-grained Personal Access
Token associated with the developer's personal GitHub account.

Authentication and authorization are treated as separate concerns:

- Authentication establishes that the factory is acting through the
  configured GitHub identity.
- Authorization determines whether that identity has the permissions
  required for the requested operation.

The factory should verify access and required permissions before attempting
operations where practical.

The factory must not assume that successful authentication means that every
requested operation is authorized.

## Credential handling

The GitHub PAT is provided through the user's shell environment, sourced
from `.zshrc`.

The token must:

- Never be committed to Git.
- Never be stored in `.factory/project.yml`.
- Never be written to application source code.
- Never be written to logs.
- Never be included in Jira comments.
- Never be included in pull-request descriptions.
- Never be printed as part of factory status or error reports.

The factory should avoid exposing the token through command output or error
messages generated by GitHub CLI, Git, or API tooling.

The project-level factory metadata contains repository identity and
configuration only. It must not contain credentials or secrets.

### Execution environments

The shell-environment sourcing model holds for interactive shells only.

Factory commands may execute in non-interactive or GUI-launched processes
that do not source `.zshrc`. Such processes inherit whatever the parent
environment exported, which may be stale, incomplete, or a placeholder
value (for example, from `launchctl`, IDE or agent launch configuration,
or another shell profile).

Therefore:

- The factory must validate authentication before its first GitHub use in
  any run, using masked diagnostics only (prefix and length).
- Remediation of an invalid inherited token is a read-only correction
  performed by the user in their launch environment. The factory never
  creates, replaces, or stores credentials.

## Permissions

The factory should use the minimum permissions required for its current
GitHub capabilities.

The initial target permissions are:

- Metadata: read
- Administration: write
- Contents: write
- Pull requests: write

The exact endpoint-level requirements must be verified during implementation
against the GitHub API being used.

Permissions must not be broadened merely for convenience.

When a new factory capability requires additional GitHub permissions, the
permission change must be reviewed rather than silently expanding the token's
scope.

## Factory approval boundaries

Authentication with GitHub does not grant the factory unrestricted
authority to act.

The factory follows these approval rules:

### Safe actions

The factory may automatically perform safe, non-destructive actions such
as:

- Inspecting repository state.
- Reading repository metadata.
- Checking Git remotes.
- Checking GitHub Actions workflow presence.
- Detecting repository state.
- Detecting local Git state.

### High-risk or externally visible actions

The factory must request explicit approval before:

- Creating a GitHub repository.
- Changing repository visibility.
- Making potentially destructive repository changes.
- Replacing or changing an existing Git remote.
- Performing other potentially destructive GitHub operations.

### Pull requests

The factory may generate a proposed pull request title and description
from the Jira Story and implementation work.

Before creating the pull request:

1. The factory presents the proposed title and description.
2. The user may review or edit them.
3. The factory creates the pull request only after explicit approval.

## Repository provisioning behavior

The authentication model supports the provisioning workflow defined by
RFC-0001.

The factory should:

1. Inspect the local Git repository.
2. Inspect the configured GitHub state.
3. Present a provisioning plan.
4. Request approval before creating an external repository.
5. Create the repository after approval.
6. Configure the repository.
7. Connect the local repository when appropriate.
8. Push the initial branch when appropriate.
9. Verify the resulting state.

If an expected repository already exists, the factory must:

- Detect it.
- Show the discovered repository to the user.
- Avoid creating another repository.
- Ask before connecting or changing anything.

## Repository visibility

The factory must ask the user whether a newly created repository should be
public or private.

The factory must not silently choose a visibility setting.

The selected visibility must be included in the provisioning plan shown before
repository creation.

## Local Git safety

Before provisioning, the factory must inspect:

- Whether the directory is a Git repository.
- Existing Git remotes.
- Current branch.
- Uncommitted changes.
- Local and remote history where relevant.

If uncommitted changes are present, the factory must show the user the
current state and allow the user to choose whether to:

- Stash the changes.
- Commit the changes.
- Discard the changes.
- Stop provisioning.

The factory must not silently commit or discard local changes.

## Push behavior

After creating a repository:

- If the newly created GitHub repository is empty, the factory may push the
  current local branch automatically after the repository-creation approval.
- If the repository is not empty, the factory must show the situation and
  ask for approval before pushing or reconciling histories.

The factory must not overwrite or force-push history without explicit
approval.

## Mismatch handling

If the local and GitHub states do not match the expected state, the factory
may automatically resolve a mismatch when the resolution is safe and
non-destructive.

Examples of safe operations include:

- Detecting an already-correct remote.
- Re-reading repository metadata.
- Refreshing locally cached factory metadata.
- Re-running a failed read-only verification.

Potentially destructive corrections require explicit approval.

Examples include:

- Replacing an existing remote.
- Changing repository visibility.
- Force-pushing.
- Removing remote history.
- Changing repository settings in a potentially destructive way.

## Project factory metadata

The factory will maintain project-level metadata in:

    .factory/project.yml

The file is committed to the project's Git repository.

The initial metadata will contain factory identity and GitHub repository
information, for example:

    factory:
      version: "1"

    github:
      owner: <github-account>
      repository: <repository-name>
      repositoryId: <repository-id>

The metadata must not contain:

- GitHub PATs.
- Passwords.
- API secrets.
- Private keys.
- Other credentials.

The metadata is a cached representation of factory-managed project state,
not the authoritative source of truth for GitHub.

The factory must verify external state when necessary rather than blindly
trusting the metadata.

## Factory versioning and metadata migration

`.factory/project.yml` contains a factory version so that the factory can
evolve its metadata format safely.

Example:

    factory:
      version: "1"

When the factory encounters an older metadata version, it may automatically
migrate the file when the migration is:

- Deterministic.
- Metadata-only.
- Non-destructive.
- Information-preserving.
- Independent of external resource changes.
- Independent of credential changes.
- Independent of application source-code changes.

Examples of safe automatic migrations include:

- Renaming a metadata field while preserving its value.
- Adding an optional field with a documented default.
- Restructuring metadata without losing information.
- Converting an equivalent representation to a new format.

The factory must request approval before migrations that could:

- Change an external repository.
- Change repository visibility.
- Change permissions.
- Change authentication configuration.
- Change Git remotes.
- Remove information.
- Change the meaning of existing configuration.

## Metadata commit approval

When provisioning creates or modifies `.factory/project.yml`, the factory
should show the proposed change and proposed commit.

The factory must request explicit approval before creating the metadata
commit.

The factory must not silently create a project-history commit solely because
factory metadata changed.

## Idempotency

GitHub operations should be safe to retry.

The factory must inspect the current state before performing an operation and
avoid unnecessarily repeating successful operations.

For example:

- An existing repository must not result in another repository.
- An existing correct `origin` must not be replaced.
- A successful repository configuration should not be repeated
  unnecessarily.
- A successfully pushed branch should not be recreated unnecessarily.
- A failed operation should be retryable from the last known successful
  stage.

## Alternatives considered

### GitHub App

**Advantages:**

- Fine-grained permissions.
- Stronger separation between the factory identity and an individual user.
- Better long-term fit for organization-level integrations.
- Installation-based authorization can provide controlled repository access.

**Disadvantages:**

- More setup and operational complexity for a personal-account-only first
  version.
- Requires application registration and installation configuration.
- Adds lifecycle and configuration overhead that is unnecessary for the
  current single-user factory.

**Decision:**

Not selected for the first version.

GitHub App authentication should be reconsidered when the factory expands
to multiple users, GitHub organizations, or other requirements where an
independent application identity provides significant value.

### Fine-grained Personal Access Token

**Advantages:**

- Simple to configure for a single developer's personal GitHub account.
- Supports repository-scoped permissions.
- Can provide the permissions required by the initial factory capabilities.
- Fits the current single-user development model.
- Low implementation complexity.

**Disadvantages:**

- Tied to the developer's GitHub identity.
- Token lifecycle and rotation are the user's responsibility.
- Less suitable as the factory becomes a multi-user or organization-wide
  service.

**Decision:**

Selected for the first version.

### OAuth / user-based authentication

**Advantages:**

- Interactive user authorization.
- Suitable for applications serving multiple users.
- Avoids requiring users to manually create a token.

**Disadvantages:**

- Adds interactive authentication infrastructure.
- More complex than required for the current single-user factory.
- Requires additional application and token lifecycle management.

**Decision:**

Not selected for the first version.

## Consequences

### Positive

- Simple authentication model for the current personal-account use case.
- Fine-grained permissions reduce unnecessary repository access.
- No GitHub App infrastructure is required initially.
- The factory can support repository creation, code pushing, and pull
  request creation.
- Credentials remain outside the project repository.
- Human approval remains the authority for externally visible and
  potentially destructive actions.
- The project metadata provides a reproducible record of the factory's
  GitHub relationship.

### Negative

- The PAT is associated with the developer's personal GitHub identity.
- Token management remains the developer's responsibility.
- The approach is less suitable for a future multi-user factory.
- Organization-level provisioning may require a different authentication
  model.
- The factory must carefully prevent token exposure through subprocess
  output and error handling.

## Security considerations

- Use a fine-grained PAT rather than a broad classic token.
- Restrict the PAT to the minimum required permissions.
- Keep the PAT in the user's shell environment.
- Never commit the PAT.
- Never store the PAT in `.factory/project.yml`.
- Never expose the PAT in logs, Jira, GitHub issues, pull requests, or
  reports.
- Do not pass the token through files that may be committed.
- Avoid printing complete environment variables during diagnostics.
- Require approval for externally visible or destructive operations.
- Fail safely when authentication or authorization fails.

## Future migration

This ADR is intentionally scoped to the factory's first single-user
GitHub provisioning capability.

When the factory expands to support:

- GitHub organizations.
- Multiple developers.
- Shared factory infrastructure.
- Centralized service identities.
- Hosted factory execution.

the authentication model should be re-evaluated.

A future ADR may select GitHub App authentication or another mechanism better
suited to those requirements.

Changing the authentication mechanism should not require changing the
factory's higher-level provisioning model.

## Amendments

### Amendment 1 — Non-interactive execution environments (2026-08-22)

The original decision is unchanged: a fine-grained PAT supplied through the
user's shell environment.

Added the "Execution environments" subsection under Credential handling.

Reason: during the 2026-08-22 AdVerify provisioning run, the factory's
non-interactive subprocesses inherited a placeholder `GITHUB_TOKEN` from the
launch environment while the valid PAT was reachable only by sourcing
`.zshrc`. Authentication failed until every command was wrapped in an
explicit `source ~/.zshrc` workaround.

Evidence: provisioning run transcript (process-environment token length 10,
placeholder value; `gh auth status` returned `401 Bad credentials`; after
sourcing `~/.zshrc`, token length 93 and `gh api repos/.../AdVerify`
returned 200).
